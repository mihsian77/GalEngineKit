# 独立实现规范（Clean Room Policy）

本项目所有代码与文档均为独立实现。本文档规定独立实现的工程纪律，确保项目在版权上干净、在创新上自主。

## 核心原则

参考外部项目的**功能规格与客观事实**是合法的；复制外部项目的**代码表达与文档文本**是不允许的。

## 五条规范

### 1. 规格先行

在实现任何模块之前，先写"我们要做什么"的功能规格文档，包括：

- 功能目标与边界
- 接口设计（函数签名、数据结构、配置项）
- 数据格式（文件格式、网络协议、存档结构等客观格式）
- 行为预期（正常流程、错误处理、边界条件）

写规格时**不打开外部项目的源代码**。规格文档放在 `docs/specs/` 下。

### 2. 实现隔离

写代码时：

- **不参考**外部项目的源代码（不打开、不对照、不凭记忆逐行复现）
- 需要引擎格式等客观信息时，只看**本项目自己整理的格式笔记**（放在 `docs/formats/`）
- 不照搬外部项目的文件结构、命名风格、模块划分
- 如确需参考某个具体实现细节，先在规格文档中记录"为什么需要参考"，再独立设计实现方案

### 3. 不复制表达

以下内容全部自己写，不复制、不逐行"翻译式改写"：

- 源代码（包括注释）
- 文档文本（README、教程、规范）
- 配置文件模板
- 测试用例（可参考测试思路，用例自己写）

### 4. 留痕

每个模块顶部必须包含独立实现声明：

```
// 独立实现：本模块为 GalEngineKit 原创实现
// 参考：<外部项目名> 的功能规格与 <引擎格式名> 等客观事实（未复制代码/文档）
// 规格文档：docs/specs/<规格文件名>.md
```

Git 提交记录应体现"规格提交 → 实现提交"的顺序：先提交规格文档，再提交实现代码。

### 5. 第三方依赖单列

- 所有第三方依赖（库、工具、代码片段）必须在文件头部与 `THIRD_PARTY_NOTICES.md` 中注明来源与许可
- 第三方依赖的许可必须与本项目 MIT 许可兼容
- **不复用**任何外部项目的二进制产物（.exe、.dll、.lib 等），全部自行编译或独立实现
- Detours（Microsoft，MIT 许可）可正常使用，但须保留其版权声明

## 违规处理

如发现任何模块违反本规范：

1. 立即标记该模块为"需重写"
2. 按规格文档重新独立实现
3. 在提交记录中说明重写原因
4. 不将违规代码合并到主分支

## 疑问

如对某段代码是否构成"复制"有疑问，请在 PR 中提出，由社区共同判断。宁可保守重写，也不留下版权隐患。
