# 对外文案规范

适用：Release notes、README、使用说明、提交说明，以及运行时日志的文案。
目的只有一个：让拿到东西的人知道这是什么、怎么用、出问题看哪，不浪费他的时间。

## 一、结构

1. 第一句说清用途、适用范围、能解决什么问题。不铺垫背景，不写项目愿景。
2. 顺序固定：怎么拿到 → 怎么用 → 出问题看哪 → 这版改了什么 → 限制。
3. 每一节一个主题，不混排。功能、限制、包内容各自成段。

## 二、用词

4. 只写可验证的。功能描述写"做了什么"，不写"有多好"。
   反例：极致兼容、丝滑体验、全面升级。正例：把日文字体替换成系统中文字体。
5. 不口语、不自嘲、不营销。不写"别抱期待""随便下一个""搞定"这类话。
6. 不替用户做判断。不确定位数这类情况，给出可执行的检查方式，不写"试试看"。
7. 中英文之间留空格；标点用中文全角；命令、文件名、路径放代码格式。

## 三、准确性

8. 没实测的不写"支持"，标"未验证"，并说明在哪验证过、缺哪一环。
9. 限制必须单独成节，写具体。例如"TFT 预渲染缓存未处理"，不写"部分场景可能不生效"。
10. 数字必须来自当前构建或实测记录，不留估算值。

## 四、运行时日志

11. 每行带时间、级别、来源模块，格式固定，便于 grep 和贴图。
12. 同一类事件合并计数，不逐条刷屏。例如字体替换只记首次与汇总次数。
13. 单文件有大小上限，超过轮转，不无限增长。
14. 错误必须写清"哪一步失败、失败在哪"，不写"出错了"。

## 五、提交说明

15. 一句话说动机，再说改了什么，最后说影响范围和回滚方式。
16. 内部实现细节写进提交说明，不搬进 Release notes。
