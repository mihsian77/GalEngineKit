# 通用钩子启动器规格文档

> 独立实现：本文档为 GalEngineKit 原创规格设计。
> 参考：Detours 进程注入机制的公开文档、RiaLoader 等同类工具的功能规格（未复制代码或文档）。
> 状态：草稿（v0.1），待实现验证后修订。

## 1. 概述

### 1.1 目标

通用钩子启动器（以下简称"启动器"）是 GalEngineKit 工具层的核心组件，负责：

1. 以挂起方式创建目标游戏进程；
2. 在进程恢复执行前，向其注入一个或多个钩子 DLL；
3. 可选地在注入前应用静态字节补丁；
4. 可选地设置进程环境变量（用于 Wine 容器配置）；
5. 恢复进程执行，并在运行期提供日志与状态反馈。

启动器的设计目标是**配置驱动、引擎无关、翻译环境友好**：用户通过一个 ini 文件描述"启动哪个游戏、注入哪些 DLL、打哪些补丁"，启动器负责执行。钩子 DLL 由各引擎适配器独立实现，启动器不关心其内部逻辑。

### 1.2 非目标

以下内容**不属于**启动器的职责范围：

- 不实现具体的字体替换或文本钩子逻辑（由插件 DLL 负责）；
- 不解析或修改游戏资源文件（由数据工具集负责）；
- 不管理 Wine 容器的创建与删除（由容器配置助手负责）；
- 不提供游戏下载、更新或版权绕过功能；
- 不支持 16 位或 DOS 程序（仅支持 32 位/64 位 Windows PE）。

### 1.3 支持的运行环境

| 环境 | 架构 | 注入方式 | 备注 |
|---|---|---|---|
| 原生 Windows | x86 / x64 | 导入表注入 / 辅助进程注入 | 全功能支持 |
| Wine（Linux/macOS） | x86 / x64 | 导入表注入 | 需 Wine 1.8+ |
| Wine + Box64（ARM64） | x86_64 翻译 | 导入表注入 / 静态补丁 | 优先静态补丁，避免运行时代码修改 |
| Wine + Box86（ARM32） | x86 翻译 | 导入表注入 / 静态补丁 | 同上 |

## 2. 术语

| 术语 | 定义 |
|---|---|
| **目标进程** | 被启动器创建并注入的游戏进程 |
| **钩子 DLL** | 被注入目标进程的动态链接库，负责具体的钩子逻辑 |
| **导入表注入** | 在进程恢复执行前，修改其 PE 导入表，将钩子 DLL 添加为导入项。进程加载器会在初始化时自动加载钩子 DLL |
| **辅助进程注入** | 通过 rundll32.exe 等辅助进程，在目标进程初始化后加载钩子 DLL。作为导入表注入的兜底方案 |
| **静态字节补丁** | 在进程恢复执行前，直接修改目标进程内存中的指令字节。不依赖任何 API 钩子，是翻译环境下最可靠的修改方式 |
| **挂起状态** | 进程被创建后主线程暂停，尚未执行任何代码的状态。此时修改内存和导入表是安全的 |

## 3. 配置文件规范

启动器使用 INI 格式的配置文件，默认与启动器同目录，名为 `GalEngineKit.ini`。也可通过命令行参数 `--config <path>` 指定。

### 3.1 完整配置示例

```ini
; GalEngineKit 启动器配置
; 分节：[Launcher] [Inject] [Patch] [Environment] [GUI]

[Launcher]
; 目标可执行文件路径（相对路径基于 WorkingDir）
TargetEXE = game.exe
; 工作目录（默认为配置文件所在目录）
WorkingDir = .
; 附加命令行参数
CommandLine = -windowed
; 创建后是否保持挂起（true 时需手动在 GUI 中点击"恢复"）
StaySuspended = false

[Inject]
; 要注入的 DLL 数量
DLLCount = 2
; DLL 路径列表（从 0 开始编号），按顺序注入
DLL_0 = hooks/krkr2_font.dll
DLL_1 = hooks/common_util.dll
; 注入方式：import_table（推荐）| helper（兜底）| auto（先尝试导入表，失败则用辅助）
InjectMethod = auto
; 注入超时（毫秒），超时后视为注入失败
TimeoutMs = 15000

[Patch]
; 静态字节补丁数量
PatchCount = 1
; 补丁文件路径（每个补丁文件可包含多条补丁规则）
Patch_0_File = patches/remove_drm.bp
Patch_0_Description = 移除启动时的版本检查

[Environment]
; 启动目标进程时设置的环境变量
; Wine 相关：DLL override、调试输出等
WINEDLLOVERRIDES = winmm=n,b;dsound=n,b
WINEDEBUG = -all,+relay
; 自定义变量
GALENGINEKIT_PROFILE = krkr2

[GUI]
; 是否启用图形界面（false 时为命令行模式，直接启动）
Enabled = true
; 启动后是否自动开始注入（false 时等待用户点击"启动"）
AutoStart = false
; 窗口标题
Title = GalEngineKit Launcher
```

### 3.2 配置校验规则

启动器在读取配置后执行以下校验，任一失败则拒绝启动并输出错误：

1. `[Launcher] TargetEXE` 必须存在且为可读文件；
2. `[Inject] DLLCount` 必须 ≥ 0，且每个 `DLL_N` 路径必须存在；
3. `[Inject] InjectMethod` 必须是 `import_table`、`helper`、`auto` 之一；
4. `[Patch] PatchCount` 必须 ≥ 0，且每个 `Patch_N_File` 必须存在且格式合法；
5. 同一 DLL 路径不得重复出现（避免重复注入）；
6. 环境变量值不得包含非法字符（如换行符）。

## 4. 启动流程

启动器的执行流程是一个确定性的状态机：

```
┌──────────┐    ┌──────────┐    ┌───────────┐    ┌──────────┐
│  读取配置 │───▶│  校验配置 │───▶│ 创建挂起  │───▶│ 应用补丁 │
│          │    │          │    │  进程     │    │ (可选)   │
└──────────┘    └──────────┘    └───────────┘    └────┬─────┘
                                                          │
                                                          ▼
┌──────────┐    ┌──────────┐    ┌───────────┐    ┌──────────┐
│  退出清理 │◀───│ 等待退出 │◀───│ 恢复主线程 │◀───│ 注入 DLL │
│ (可选)   │    │ (可选)   │    │           │    │ (核心)   │
└──────────┘    └──────────┘    └───────────┘    └──────────┘
```

### 4.1 状态定义

| 状态 | 说明 | 失败处理 |
|---|---|---|
| `CONFIG_LOAD` | 读取并解析 ini 文件 | 输出错误，退出码 1 |
| `CONFIG_VALIDATE` | 校验配置项合法性 | 输出具体错误，退出码 2 |
| `PROCESS_CREATE` | 以 `CREATE_SUSPENDED` 创建目标进程 | 输出错误，退出码 3 |
| `PATCH_APPLY` | 应用静态字节补丁（可选） | 输出警告，可选择继续或中止 |
| `DLL_INJECT` | 注入钩子 DLL | 回滚（终止进程），退出码 4 |
| `THREAD_RESUME` | 恢复主线程执行 | 终止进程，退出码 5 |
| `RUNNING` | 目标进程运行中，启动器等待 | 记录退出码 |
| `CLEANUP` | 清理临时资源（可选） | — |

### 4.2 详细步骤

**步骤 1：读取与校验配置**
- 解析 ini 文件，建立配置对象；
- 执行 3.2 节的校验规则；
- 将所有相对路径转换为基于 `WorkingDir` 的绝对路径。

**步骤 2：创建挂起进程**
- 调用 `CreateProcessW`，传入 `CREATE_SUSPENDED` 标志；
- 工作目录设为 `WorkingDir`；
- 环境块合并当前环境 + `[Environment]` 节中的变量；
- 保存进程句柄、主线程句柄和进程 ID。

**步骤 3：应用静态字节补丁（可选）**
- 读取每个 `.bp` 补丁文件；
- 对每条补丁规则，在目标进程内存中定位目标地址；
- 先读取原始字节，与规则中的"原始字节"比对（防止版本不匹配）；
- 比对一致则写入"补丁字节"；
- 比对不一致则输出警告，根据配置决定继续或中止。

**步骤 4：注入 DLL**
- 按 `DLL_0` 到 `DLL_N` 的顺序注入；
- 优先使用导入表注入（见 5.1 节）；
- 若导入表注入失败且 `InjectMethod=auto`，回退到辅助进程注入（见 5.2 节）；
- 每个 DLL 注入后，检查其是否已出现在目标进程的模块列表中；
- 全部注入成功后进入下一步；任一失败则终止目标进程并报错。

**步骤 5：恢复主线程**
- 调用 `ResumeThread` 恢复目标进程主线程；
- 若 `StaySuspended=true`，则跳过此步，等待用户在 GUI 中手动恢复。

**步骤 6：运行期监控（可选）**
- 若启用 GUI，显示目标进程状态（运行中/已退出/退出码）；
- 启动器可选择等待目标进程退出后自动关闭，或保持运行供日志查看。

## 5. 进程注入机制

### 5.1 导入表注入（推荐）

导入表注入是首选方式，原理是在目标进程挂起状态下，修改其 PE 导入表，将钩子 DLL 添加为第一个导入项。当目标进程恢复执行时，Windows 加载器会在进程初始化阶段自动加载钩子 DLL，并调用其 `DllMain`。

**优点**：
- 注入发生在进程执行任何代码之前，时序最干净；
- 不依赖运行时 API 钩子，对翻译环境（Box64/Box86）友好；
- 支持同时注入多个 DLL，按导入表顺序加载。

**实现要点**：
- 使用 `DetourUpdateProcessWithDll`（Detours 库提供）或独立实现等价的 PE 导入表修改逻辑；
- 修改前备份原始导入表，注入失败时可回滚；
- 钩子 DLL 的 `DllMain` 中应尽快返回，避免在 `DLL_PROCESS_ATTACH` 中执行耗时操作（加载器锁限制）。

### 5.2 辅助进程注入（兜底）

当导入表注入不可用时（如目标进程的 PE 结构异常、或导入表已被其他工具修改），使用辅助进程注入作为兜底。

**原理**：
- 启动一个 `rundll32.exe` 辅助进程，传入钩子 DLL 路径和导出函数名；
- 辅助进程通过 `CreateRemoteThread` 或 `QueueUserAPC` 在目标进程中加载钩子 DLL；
- 此方式发生在目标进程初始化之后，时序不如导入表注入干净。

**限制**：
- 在某些翻译环境下，`CreateRemoteThread` 可能不稳定；
- 钩子 DLL 的 `DllMain` 执行时，目标进程可能已经初始化了部分子系统。

### 5.3 注入顺序与依赖

当注入多个 DLL 时，按配置中的 `DLL_0` 到 `DLL_N` 顺序注入。若 DLL 之间存在依赖关系（如 `common.dll` 必须先于 `krkr2_font.dll` 加载），用户需在配置中按依赖顺序排列。启动器不自动解析 DLL 依赖。

## 6. 插件 DLL 接口规范

钩子 DLL 是启动器的"插件"，负责具体的引擎适配逻辑。启动器与插件 DLL 之间通过以下约定交互。

### 6.1 必需接口

每个钩子 DLL 必须是标准 Windows PE 动态链接库，导出标准入口 `DllMain`。启动器不要求 DLL 导出任何特定函数——注入后，DLL 在 `DllMain(DLL_PROCESS_ATTACH)` 中自行完成钩子安装。

### 6.2 可选接口

为了与启动器的 GUI 和日志系统集成，钩子 DLL 可选择性地导出以下函数：

```c
// 返回插件信息（名称、版本、引擎ID、描述）
// 启动器在注入成功后调用，用于显示插件列表
typedef struct {
    const wchar_t* name;           // 插件名称，如 "KiriKiri Font Hook"
    const wchar_t* version;        // 版本字符串，如 "1.0.0"
    const wchar_t* engine_id;      // 适配的引擎ID，如 "krkr2"
    const wchar_t* description;    // 简短描述
} GalEngineKitPluginInfo;

const GalEngineKitPluginInfo* GalEngineKit_GetInfo(void);

// 初始化回调，启动器在注入后调用（可选）
// config_section 为该 DLL 在配置文件中的自定义节名
// 返回 0 表示成功，非零表示初始化失败
int GalEngineKit_Init(const wchar_t* config_section);
```

### 6.3 钩子安装约束

钩子 DLL 在安装钩子时必须遵守以下约束（由 clean-room 规范和翻译环境兼容性共同要求）：

1. **只钩游戏自身代码**：钩子目标必须是游戏主模块或游戏自带 DLL 中的函数，不得挂钩 Wine 内置 DLL（如 `kernel32.dll`、`user32.dll`、`gdi32.dll`）的导出函数。如需拦截系统 API，应通过游戏代码中调用该 API 的位置间接挂钩；
2. **优先使用执行前修改**：能通过静态字节补丁解决的，不使用运行时内联钩子；
3. **钩子必须可禁用**：每个钩子应支持通过配置项开关，便于调试和问题定位；
4. **线程安全**：钩子回调必须考虑多线程环境，使用适当的同步机制；
5. **不修改只读段**：运行时不得修改代码段的内存属性（如调用 `VirtualProtect` 将代码段设为可写），这在翻译环境下可能导致翻译缓存失效。

### 6.4 配置传递

启动器将整个 ini 配置文件的路径通过环境变量 `GALENGINEKIT_CONFIG` 传递给目标进程。钩子 DLL 可读取此环境变量，定位配置文件，并读取自己的自定义节（如 `[HookFont]`、`[Krkr2]`）获取配置。

示例：
```ini
; 启动器配置中的自定义节，由 krkr2_font.dll 读取
[Krkr2]
EnableFontHook = 1
FontName = 微软雅黑
EnablePreRenderCache = 0
```

## 7. 静态字节补丁

### 7.1 补丁文件格式

静态字节补丁使用纯文本文件（`.bp` 扩展名），每行一条补丁规则。支持 `;` 开头的注释行和空行。

**规则格式**：
```
<地址> : <原始字节> -> <补丁字节>
```

- **地址**：可以是 RVA（相对虚拟地址，如 `0x00012345`），或 `模块名:RVA`（如 `game.exe:0x00005678`）。不指定模块时默认为目标主模块；
- **原始字节**：空格分隔的十六进制字节，如 `90 90`。应用补丁前会比对，不一致则警告；
- **补丁字节**：空格分隔的十六进制字节，如 `E8 00 00 00 00`。长度必须与原始字节相同。

**示例**：
```bp
; 移除版本检查（将 JE 改为 JMP）
game.exe:0x00012345: 74 03 -> EB 03

; NOP 掉一个函数调用
0x00005678: E8 12 34 56 78 -> 90 90 90 90 90

; 多字节补丁
0x0000ABCD: 8B 45 08 85 C0 -> 33 C0 90 90 90
```

### 7.2 应用流程

1. 读取 `.bp` 文件，解析每条规则；
2. 对每条规则：
   a. 根据模块名和 RVA 计算目标进程中的绝对地址；
   b. 调用 `ReadProcessMemory` 读取原始字节；
   c. 与规则中的原始字节比对；
   d. 一致则调用 `WriteProcessMemory` 写入补丁字节；
   e. 不一致则输出警告（包含期望字节和实际字节），根据 `PatchOnMismatch` 配置决定继续或中止。
3. 全部补丁应用完成后，输出补丁应用报告（成功/跳过/失败数量）。

### 7.3 安全约束

- 补丁文件中不得包含对 Wine 内置 DLL 的补丁（只允许补丁游戏主模块和游戏自带 DLL）；
- 补丁地址必须在模块的代码段或数据段范围内，不得写入不可访问的内存；
- 启动器在应用补丁前会验证地址的可读性和可写性。

## 8. 环境变量管理

启动器在创建目标进程时，将 `[Environment]` 节中的变量合并到目标进程的环境块中。

**合并规则**：
- `[Environment]` 中的变量覆盖当前进程的同名变量；
- 未在 `[Environment]` 中出现的变量，继承当前进程环境；
- 变量值中的分号 `;` 视为路径分隔符（如 `WINEDLLOVERRIDES`）。

**Wine 常用环境变量**：

| 变量 | 用途 | 示例 |
|---|---|---|
| `WINEDLLOVERRIDES` | DLL 覆盖（原生/内建） | `winmm=n,b` |
| `WINEDEBUG` | 调试输出控制 | `-all,+relay` |
| `WINEPREFIX` | Wine 前缀路径 | `/home/user/.wine` |
| `WINESERVER` | Wine 服务器路径 | `/usr/bin/wineserver` |
| `SDL_VIDEODRIVER` | SDL 视频驱动 | `x11` / `wayland` |

## 9. 日志与错误处理

### 9.1 日志级别

启动器使用四级日志：

| 级别 | 标识 | 用途 |
|---|---|---|
| 错误 | `[ERROR]` | 导致启动失败的错误 |
| 警告 | `[WARN]` | 不影响启动但需注意的情况（如补丁比对不一致） |
| 信息 | `[INFO]` | 正常流程信息（如"进程已创建"、"DLL 注入成功"） |
| 调试 | `[DEBUG]` | 详细调试信息（默认不输出） |

### 9.2 日志输出

- 日志同时输出到控制台（stdout/stderr）和日志文件；
- 日志文件默认路径：`<WorkingDir>/logs/galenginekit_<timestamp>.log`；
- 日志文件大小超过 10MB 时自动轮转（保留最近 5 个）；
- 可通过配置 `[Launcher] LogLevel = debug` 调整输出级别。

### 9.3 退出码

| 退出码 | 含义 |
|---|---|
| 0 | 启动成功，目标进程正常退出（启动器等待模式） |
| 1 | 配置文件读取失败 |
| 2 | 配置校验失败 |
| 3 | 进程创建失败 |
| 4 | DLL 注入失败 |
| 5 | 线程恢复失败 |
| 6 | 补丁应用失败且配置为中止 |
| 10 | 用户取消（GUI 模式下点击"取消"） |

## 10. 动态二进制翻译环境适配

启动器在 Wine + Box64/Box86 等动态二进制翻译环境下运行时，需采取以下适配策略：

### 10.1 注入方式选择

- **优先导入表注入**：导入表注入发生在进程执行前，纯内存写入，不触发翻译缓存失效，是翻译环境下最稳定的注入方式；
- **静态字节补丁作为兜底**：当导入表注入不可用时，静态字节补丁（执行前写内存）是次优选择；
- **避免辅助进程注入**：`CreateRemoteThread` 在翻译环境下可能不稳定，仅作为最后手段。

### 10.2 钩子目标限制

- 钩子 DLL 必须严格遵守 6.3 节的约束，只钩游戏自身代码；
- 挂钩 Wine 内置 DLL 的导出函数在翻译环境下极其脆弱：Wine 的内置 DLL 是 ARM64 原生代码（在 Box64 环境下），x86 内联钩子打在 ARM64 代码上会直接崩溃；
- 即使 Wine 内置 DLL 有 x86 版本（wow64 模式），挂钩其代码也可能干扰翻译器的缓存机制。

### 10.3 环境变量优化

- 在翻译环境下，建议设置 `WINEDEBUG=-all` 以减少调试输出对性能的影响；
- 对于需要 DXVK 的游戏，确保 `WINEDLLOVERRIDES` 中包含 `d3d9=n,d3d11=n,dxgi=n`；
- 单线程游戏可考虑设置 `WINEDEBUG=-all` 和 `STAGING_SHARED_MEMORY=0` 以减少开销。

## 12. 安全与合规

### 12.1 安全设计

- 启动器不修改系统文件或注册表（所有修改限于目标进程内存）；

- 补丁文件在应用前进行地址合法性校验；
- 日志文件不记录敏感信息（如密码、密钥）。

### 12.2 合规声明

- 若使用 Detours 库实现注入逻辑，Detours 为 MIT 许可，需在 `THIRD_PARTY_NOTICES.md` 中声明；
- 启动器不包含任何游戏资源或版权材料；
- 用户需自行确保使用启动器修改游戏符合当地法律和游戏 EULA。

## 14. 待决问题

以下问题在实现阶段需要进一步验证和决策：

1. **Detours 依赖 vs 自研注入**：是直接使用 Detours 库（MIT，成熟稳定），还是独立实现 PE 导入表修改逻辑（零依赖，但开发量大）？建议初期使用 Detours，后续可替换为自研实现。
2. **x86/x64 双版本**：启动器是否需要同时提供 32 位和 64 位版本？32 位启动器只能注入 32 位进程，64 位启动器只能注入 64 位进程。建议提供双版本，或在启动器中自动检测目标进程架构并调用对应版本。
3. **Wine 下的进程创建**：`CreateProcessW` 在 Wine 下的行为与原生 Windows 是否完全一致？需在 Wine 7+ 和 Wine + Box64 环境下实测验证。
4. **GUI 框架选择**：Win32 API（原生但开发量大）、nana（轻量 C++ GUI）、libui（跨平台 C GUI）？需评估体积、依赖和开发效率。
